# 脅威モデル

## 守るもの

| 資産 | 説明 |
|---|---|
| 通知の内容 | チャンネル名、送信者名、本文（業務情報） |
| AES 鍵 | 通知を復号するための鍵（ASCII 32 文字） |
| device_key | bark-server 上の送信先 ID |
| 通知センター DB | Mac 上のすべてのアプリの通知履歴 |

## 信頼する相手

- **Apple APNs**：暗号文と、APNs のメタデータ（デバイストークン、送信時刻）だけを見る
- **Bark iOS アプリ**（Finb/Bark、MIT ライセンス）：Notification Service Extension の中で、端末上の鍵を使って復号する。解析やトラッキング用の SDK はない。履歴は端末内にだけ保存される
- **bark-server**（Finb/bark-server、バージョンと SHA256 を固定）：外向きの通信先は `api.push.apple.com` だけ
- **macOS**（キーチェーン、TCC）

## 対策

| 脅威 | 対策 |
|---|---|
| 経路上（APNs を含む）で内容を読まれる | AES-256-GCM で端末間を暗号化する。IV はメッセージごとにランダム。送るパラメータは `ciphertext` と `iv` だけ（テストで保証） |
| LAN 上の他の端末が bark-server を使う | 通常運用は `127.0.0.1` でだけ待ち受ける。ループバック以外はコードで拒否する。`register` だけはプライベート IP・5 分限定・明示的な実行が条件 |
| 環境変数で待ち受けアドレスやプロキシが変わる | 子プロセスには最小限の環境変数だけを渡す。HTTP クライアントはプロキシを使わず、リダイレクトにも従わない |
| ログから内容が漏れる | allow list 方式でマスクするロガーを使う（debug モードでも同じ）。bark-server のアクセスログは捨てる。送信エラーは種類だけを残す |
| ps から秘密情報が見える | 秘密情報はコマンドライン引数に載せない（`security -i` の標準入力を使う） |
| ローカルの他ユーザーがファイルを読む | `~/.slack-relay` は `0700`、中のファイルは `0600`（umask `0077`）。起動時に確認して警告する |
| 通知 DB を壊す | 読み取り専用で開く（`mode=ro`、`query_only`）。書き込みは一切しない |
| リポジトリから秘密情報が漏れる | 秘密情報はキーチェーンにだけ置く。gitleaks（pre-commit と CI）、Secret scanning、Push protection |
| サプライチェーン | `go.sum`、`go mod verify`、govulncheck、Dependabot を使う。Actions はコミット SHA で固定する。bark-server はバージョンと SHA256 で固定する |

## 残るリスク

- **偽の通知を送られる**：APNs 送信用の鍵は上流で公開されている（Bark アプリの公式な鍵）。そのため、デバイストークンを知っている人は、自分のサーバーから偽の通知を送れる。内容を読むことはできない。正しい鍵で暗号化されていない通知は「Decryption Failed」になるので、見分けられる
- **公式サーバーへのデバイストークン登録**：Bark アプリは初回起動時に、公式サーバー（api.day.app）にデバイストークンを登録する。トークンを知られることは、上の「偽の通知」のリスクにつながる
- **メタデータ**：APNs は、通知を送った時刻と頻度を知ることができる
- **`register` 中の LAN への公開**：最大 5 分間、同じ LAN 上の端末が bark-server に到達できる（認証なし）。この間に別の端末がデバイスを登録したり、既知の device_key に push したりできる
- **ローカルのマルウェアや同じユーザー権限のプロセス**：キーチェーンの読み出し、loopback 上の bark-server への送信、通知 DB の読み取りができてしまう。本ツールの範囲外
- **iPhone 上の履歴**：復号した通知は、Bark アプリの端末内 DB に残る
- **bark-server の MCP エンドポイント**：v2.3.7 には MCP 関連のルートがある。ループバックでしか待ち受けないため、外部からは到達できない
